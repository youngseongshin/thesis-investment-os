# Politics Tracker 설계안 (가칭: 발언록)

> 정치인의 말을 시간축 위에 기록하고, 출처와 함께 공개하고, 검증 가능한 지표로만 평가한다.
>
> 판정은 사이트가 아니라 독자가 한다. 사이트는 근거를 제공한다.

국내 주요 정치인, 관료, 국회의원이 정치·의정활동에서 어떤 발언을 해왔는지 추적해 보여주고 평가하는 공개 사이트의 설계안이다. Thesis OS와는 별개 프로젝트이지만 같은 사상을 공유한다: **설득력이 아니라 사후 책임성(accountability)**. 발언을 사후에 수정할 수 없는 기록으로 남기고, 시간이 지난 뒤 말과 행동(표결·공약 이행·예측 결과)을 대조한다.

로컬 작업 폴더: `~/Documents/Codex/2026-08-16/politics-tracker`

---

## 1. 문제 정의

- 정치인의 발언은 뉴스 사이클과 함께 휘발된다. 6개월 전 발언과 오늘 발언을 나란히 놓고 보는 도구가 없다.
- 언론의 팩트체크는 개별 발언 단위로 끝난다. **인물 단위의 누적 기록** — 입장 변화, 말과 표결의 불일치, 공약 이행 — 은 아무도 체계적으로 축적하지 않는다.
- 기존 유사 서비스(의정활동 평가 지표, 열려라국회 류)는 출석률·발의 건수 같은 활동량 지표에 머물고, **발언 내용의 시계열**은 다루지 않는다.
- 국회 회의록·표결·의안 데이터는 이미 공공 API로 전부 공개되어 있다. 문제는 데이터가 아니라 **가공과 접근성**이다.

## 2. 설계 원칙

1. **모든 주장에 원문 링크.** 발언 하나하나가 회의록 원문, 공식 브리핑, 기사 원문으로 클릭 한 번에 연결된다. 출처 없는 발언은 싣지 않는다.
2. **평가는 지표로, 판정은 독자에게.** "좋은 정치인/나쁜 정치인"을 사이트가 선언하지 않는다. 발언–표결 일치도, 입장 변화 횟수, 공약 이행률처럼 **기계적으로 재현 가능한 지표**만 산출하고, 모든 점수는 근거 발언 목록으로 drill-down된다.
3. **입장 변화는 죄가 아니라 기록이다.** 입장이 바뀐 사실과 시점, 당시 맥락(당적 변경, 여야 교대, 새로운 사실의 등장)을 병기한다. 낙인이 아니라 이력이다.
4. **방법론 전체 공개.** 수집 코드, 분류 기준, LLM 프롬프트, 채점 규칙을 오픈소스로 공개한다. 편향 시비에 대한 최선의 방어는 재현 가능성이다.
5. **기계가 추출하고 사람이 확정한다.** LLM 추출 결과 중 신뢰도가 낮은 것은 공개 전 인간 검수 큐를 거친다. 공개 후에도 당사자 이의제기 채널을 상시 운영한다.
6. **정적 우선, 저비용 우선.** 수집·추출은 배치 파이프라인, 사이트는 정적 생성 위주. 1인 운영자가 월 몇만 원 수준으로 유지할 수 있는 구조에서 시작한다.

## 3. 대상 범위

| 단계 | 인물 스코프 | 근거 |
|---|---|---|
| 시작 | 현역 국회의원 300명 | 명부·발언·표결이 전부 공공 API로 구조화되어 있어 자동화가 가장 쉽다 |
| 확장 1 | 국무위원(장관), 대통령실 주요 참모 | 국회 출석 발언 + 정부 공식 브리핑으로 추적 가능 |
| 확장 2 | 광역단체장, 주요 당직자, 대선 주자군 | 언론 인용문 의존도가 높아져 파이프라인 성숙 후 진행 |

"주요 정치인"의 경계는 자의적 판단을 피하기 위해 **직위 기반 규칙**으로 정의한다(현역 의원 전원, 국무위원 전원, 정당 대표·원내대표 등). 개별 선별은 하지 않는다.

## 4. 핵심 사용자와 시나리오

- **유권자**: 인물 검색 → 발언 타임라인 → 주제별 입장 → "이 사람이 부동산에 대해 뭐라고 해왔나"를 3분 안에 파악.
- **기자·연구자**: 전문 검색, 필터(기간·주제·인물·회의체), 인용 가능한 퍼머링크, 데이터 다운로드/API.
- **선거 시기 사용자**: 지역구/비례 후보 비교 — 같은 주제에 대한 두 인물의 발언 이력을 나란히.
- **당사자(의원실)**: 본인 발언 기록 확인, 오류 정정 요청.

## 6. 도메인 모델

```text
Person(인물) ─ PositionHistory(직위 이력: 의원·장관·당직, 당적 변경 포함)
   │
   ├─ Utterance(발언) ── SourceDocument(원문: 회의록·브리핑·기사)
   │      │                └ 원문 URL, 아카이브 스냅샷, 수집 시각
   │      ├─ Topic(주제 분류: 부동산·노동·외교안보·…)
   │      └─ Stance(입장: 주제별 방향 + 신뢰도 + 추출 근거)
   │
   ├─ Vote(표결) ── Bill(의안)
   ├─ Pledge(공약) ── PledgeStatus(이행 판정 + 근거 링크)
   ├─ Prediction(예측성 발언) ── Outcome(사후 채점)
   └─ CorrectionRequest(정정 요청 이력 — 그 자체를 공개 기록으로)
```

발언(utterance) 레코드 예시:

```json
{
  "utterance_id": "utt_2026_na_pl_0412_0038",
  "person_id": "per_kr_na_XXXX",
  "spoken_at": "2026-04-12",
  "venue": {"type": "assembly_plenary", "session": "제22대 제412회 제3차 본회의"},
  "text": "발언 원문 문단...",
  "context_window": {"before": "...", "after": "..."},
  "source": {
    "kind": "assembly_minutes",
    "url": "https://likms.assembly.go.kr/record/...",
    "archived_snapshot": "s3://.../snap.html",
    "collected_at": "2026-04-13T02:00:00+09:00"
  },
  "topics": [{"topic": "real_estate", "confidence": 0.93}],
  "stance": {
    "topic": "real_estate",
    "axis": "regulation_strengthen_vs_relax",
    "value": -0.6,
    "confidence": 0.81,
    "rationale_quote": "판단 근거가 된 원문 구절",
    "extractor": {"model": "claude-*", "prompt_version": "stance_v3"},
    "human_reviewed": false
  }
}
```

설계 포인트:

- **원문 스냅샷 보존**: 출처 링크가 죽어도 검증 가능하도록 수집 시점 스냅샷을 보관한다(공공저작물은 저장 가능, 기사는 인용문+메타데이터만).
- **추출기 버전 기록**: 어떤 모델·프롬프트 버전이 분류했는지 레코드에 남긴다. 방법론이 바뀌면 재채점하고 이력을 남긴다.
- **stance는 주제별 축(axis) 위의 값**: "찬반"으로 뭉개지 않고 주제마다 축을 정의한다(예: 부동산 = 규제 강화 ↔ 완화). 축 정의 자체도 공개 문서로 관리한다.
- **동명이인**: 화자 매칭은 이름 + 회의체 소속 + 대수(代數) 교차 검증으로 해소한다. 회의록의 `홍길동 위원` 표기만으로는 부족한 경우가 실제로 있다.

## 7. 데이터 파이프라인

```text
1 수집   per-source adapter가 원문을 raw 저장 (멱등, 재실행 안전)
2 파싱   회의록 → 발언 단위 분리 (규칙 기반, LLM 불필요)
3 매칭   화자 문자열 → person_id (동명이인 교차 검증)
4 분류   주제 태깅 (LLM, 다중 라벨 + confidence)
5 추출   입장/예측성 발언 추출 (LLM, structured output)
6 검수   confidence < 임계값 → 인간 검수 큐, 통과분만 공개
7 게시   공개 DB 반영 → 사이트 재생성 → 지표 재계산
```

- 각 단계는 독립 배치 잡이다. 초기에는 GitHub Actions cron(일 1회)으로 충분하고, 전용 워커는 규모가 커진 뒤에 도입한다.
- LLM 호출은 배치 API로 묶어 비용을 절반으로 줄인다. 주제 분류처럼 단순한 작업은 소형 모델(Haiku급), 입장 추출·예측 판정처럼 미묘한 작업만 상위 모델을 쓴다.
- 대략의 규모 감각: 본회의·상임위 회의록은 연간 수천 건, 발언 단위로는 수십만 건 수준. 파싱(2단계)까지는 LLM 비용이 0이고, 분류·추출은 증분(새 회의록만) 처리이므로 정상 운영 시 월 LLM 비용은 수만~수십만 원대에서 통제 가능하다. 과거분 백필은 1회성 비용으로 분리해 집행한다.

## 8. 평가 방법론 — 이 프로젝트의 성패가 갈리는 부분

원칙: **사이트는 형용사를 쓰지 않는다. 숫자와 근거 목록만 낸다.** 모든 지표는 클릭하면 계산에 사용된 발언·표결 목록이 그대로 펼쳐진다(evidence-linked scoring).

| 지표 | 정의 | 검증 가능성 |
|---|---|---|
| **말–표 일치도** | 법안 관련 발언에서 추출한 입장 vs 실제 본회의 표결의 일치 비율 | 표결은 공식 기록이므로 완전 기계 검증 |
| **입장 일관성** | 동일 주제 축 위에서 입장 값의 시계열 변화 횟수·폭. 변화 시점에 맥락 주석(당적 변경 등) 병기 | LLM 추출 기반 — 근거 인용구 필수, 저신뢰 건 인간 검수 |
| **공약 이행** | 선관위 공약집 기준 이행/부분 이행/미이행/검증 불가 4단계 + 근거 링크 | 판정 기준을 공약별로 사전 명시 |
| **예측 채점** | "~될 것이다" 류의 검증 가능한 예측성 발언만 등록. 마감일과 판정 기준을 등록 시점에 고정하고 사후 채점 | Thesis OS의 prediction ledger 사상 그대로. 사후 수정 불가 |
| **팩트체크 집계** | 외부 팩트체크 기관의 판정 결과를 인용·집계. 자체 판정 없음 | 출처 기관 명시 |

**의도적으로 만들지 않는 것**: 종합 점수, 랭킹, 등급. 지표를 하나의 숫자로 합산하는 순간 가중치라는 이름의 편향이 들어가고, 사이트가 심판이 된다. 지표는 병렬로 보여주고 해석은 독자에게 맡긴다.

편향 통제 장치:

- **정당 균형 감사**: 파이프라인이 특정 정당 인물의 발언을 더 많이/적게 추출하거나, 입장 추출 오류율이 정당별로 다른지 분기마다 표본 감사해 결과를 공개한다.
- **프롬프트·기준 공개**: 입장 추출 프롬프트, 주제 축 정의, 공약 판정 기준을 저장소에 버전 관리로 공개한다.
- **이의제기 → 공개 기록**: 당사자 정정 요청과 처리 결과를 해당 발언 페이지에 그대로 남긴다. 정정 이력 자체가 신뢰의 근거가 된다.

## 9. 제품 구성 (페이지)

1. **인물 페이지** — 프로필(직위·당적 이력 타임라인 포함), 발언 타임라인(주제·기간 필터), 주제별 입장 차트, 지표 카드 4종, 표결 이력, 정정 이력.
2. **주제 페이지** — 주제 축 정의, 이 주제에 대해 발언한 인물들의 입장 분포와 시계열, 관련 의안.
3. **발언 상세(퍼머링크)** — 원문, 앞뒤 맥락, 출처 링크·스냅샷, 추출 메타데이터(모델·버전·검수 여부), 공유용 카드 이미지.
4. **비교 페이지** — 인물 2~4명의 같은 주제 발언 이력 나란히 보기. 선거 모드의 핵심.
5. **검색** — 전문 검색 + 필터(인물·기간·회의체·주제). 한국어 형태소 대응.
6. **방법론 페이지** — 지표 정의, 데이터 출처, 프롬프트, 감사 리포트, 정정 절차. 이 사이트의 헌법.

## 10. 시스템 아키텍처

```text
politics-tracker/
├── apps/web            Next.js (App Router, SSG/ISR) — 인물·발언 페이지는 정적 생성
├── pipelines/          Python 배치 (수집·파싱·매칭·분류·추출·지표 계산)
│   ├── sources/        assembly_api / minutes / briefing / nec ... (adapter별)
│   └── extract/        LLM 분류·입장 추출 (프롬프트 버전 관리 포함)
├── db/                 Postgres 마이그레이션 (+pgvector, 유사 발언 검색용)
├── schemas/            utterance / stance / pledge / prediction JSON Schema
└── docs/               방법론 문서 = 사이트 방법론 페이지의 원본
```

기술 선택과 이유:

- **DB: Postgres** (Supabase 또는 Fly.io). 관계(인물–발언–표결–의안)가 본질인 데이터라 문서형 DB보다 낫다. pgvector로 유사 발언 탐색(입장 변화 후보 발굴)까지 커버.
- **검색: Meilisearch**. 한국어 토크나이징 지원이 실용적이고 셀프호스팅이 가볍다. Phase 1부터 도입, 그 전엔 Postgres FTS로 버틴다.
- **프론트: Next.js 정적 생성 위주**. 데이터 갱신이 일 1회 배치이므로 실시간성이 필요 없다. 트래픽이 튀어도(방송 언급 등) 정적 페이지는 버틴다.
- **파이프라인 실행: GitHub Actions cron → 규모 확대 시 전용 워커**. 초기 인프라 비용을 사실상 0으로.
- **LLM: Claude API** — 분류는 소형 모델, 입장·예측 추출은 상위 모델, 전부 structured output + 배치 API.

## 11. 법적·윤리 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 명예훼손 | 사실 적시(발언 원문 인용) + 출처 명시 + 공공의 이익 목적이라는 3요소를 모든 콘텐츠에서 유지. 평가는 8장의 기계적 지표로 한정하고 인신 논평을 싣지 않는다. 공개 전 법률 자문으로 표현 가이드라인 확정 |
| 공직선거법 | 선거기간 중 후보자 비교·여론조사 공표 관련 규제가 복잡하다. **선거 90일 전 시점의 기능 운영 방침(비교 페이지 표시 방식 등)은 반드시 사전 법률 자문**을 받아 별도 운영 모드로 설계한다 |
| 저작권 | 공공저작물(회의록·브리핑)은 원문 게재, 언론 기사는 직접 인용문 발췌+링크만(전문 저장·재게시 금지). 소스별 저작권 정책을 adapter 코드에 명시 |
| 오추출·오귀속 | 저신뢰 추출 인간 검수, 동명이인 교차 검증, 발언 페이지에 추출 메타데이터 공개, 당사자 정정 채널. 오류 정정은 24~72시간 SLA를 방법론 페이지에 공언 |
| 편향 시비 | 코드·프롬프트·감사 리포트 공개(8장). 운영자의 정치적 후원·당적 이해충돌 고지 정책 |
| 개인정보 | 공인의 공적 발언만 다룬다. 사생활 영역 발언·가족 관련 내용은 수집 단계에서 배제 규칙으로 필터링 |

## 12. 로드맵

| 단계 | 기간(감각) | 내용 | 성공 기준 |
|---|---|---|---|
| **Phase 0 — 뼈대** | 2~3주 | 열린국회정보 API로 의원 300명 프로필 + 최근 1년 본회의 회의록 파싱 → 인물별 발언 타임라인 정적 사이트. **LLM 없이 완성 가능** | 임의 의원 검색 → 실제 발언과 원문 링크가 정확히 나온다 |
| **Phase 1 — 검색과 주제** | +4주 | 상임위 회의록 추가, LLM 주제 분류, Meilisearch 전문 검색, 발언 퍼머링크 | "○○의원 부동산 발언"이 필터 두 번으로 나온다 |
| **Phase 2 — 입장과 표결** | +6주 | 입장 추출 + 시계열 차트, 입장 변화 감지, 말–표 일치도, 인간 검수 큐 | 지표 → 근거 발언 drill-down이 끊김 없이 동작. 표본 감사 오류율 목표치 이내 |
| **Phase 3 — 평가 완성** | +8주 | 공약 추적, 예측 채점, 팩트체크 연계, 방법론 페이지, 정정 채널, 언론 인용문(파일럿) | 외부 기자가 기사에 인용할 수 있는 수준의 신뢰도 |
| **Phase 4 — 공개 재화** | 이후 | 공개 API·데이터 덤프, 비교 페이지 선거 모드, 관료·단체장 확장 | 제3자가 이 데이터로 뭔가를 만든다 |

Phase 0의 요점: **LLM도, 평가도 없이 "정확한 타임라인 + 원문 링크"만으로 이미 존재하지 않던 가치가 성립한다.** 평가 기능은 그 신뢰 위에만 쌓을 수 있다.

## 13. 열린 결정 사항

- **이름**: 가칭 "발언록". 후보: 말의기록, 온말, 폴리로그. 도메인 확보와 함께 결정.
- **운영 주체 형태**: 개인 프로젝트로 시작하되, Phase 3 이후 비영리 등록 여부 검토(언론중재법·선거법 대응 관점에서 유리한 형태 자문 필요).
- **언론 인용문 도입 시점**: 파이프라인 정확도와 정정 절차가 검증된 뒤로 보수적으로 판단.
- **수익/지속 모델**: 광고 없음 전제. 후원 + 공공데이터 활용 지원사업 정도를 상정하되 MVP 단계에서는 결정하지 않는다.
